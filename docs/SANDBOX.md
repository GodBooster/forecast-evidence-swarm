# Local NEAR Sandbox integration

**Harness status: compiled and executed on 2026-11-08.** `sandbox/tests/near_sandbox.rs`
contains two integration tests. Each deploys the `forecast_jobs` WASM to its own fresh,
ephemeral local NEAR Sandbox node, creates local test accounts, and checks onchain job
state, receipts, account balances and the contract's outstanding reward liability. No
Testnet or Mainnet is used. See "Executed runs" below. This is a local-chain prototype check, not a security
audit, a public deployment or evidence of forecasting skill.

## Run it

From the repository root, with Docker running:

```sh
bash sandbox/run.sh
```

The wrapper regenerates the synthetic core report, builds `contracts/forecast_jobs` for
`wasm32-unknown-unknown` on the host with the `1.99.1` toolchain in `--offline` mode
(one-time setup: `rustup toolchain install 1.99.1`, `rustup target add
wasm32-unknown-unknown --toolchain 1.99.1`, `cargo +1.99.1 fetch --manifest-path
contracts/forecast_jobs/Cargo.toml`), then starts one
resource-limited Linux container. The runner image `forecast-near-runner:1.99` is built
once from `sandbox/runner.Dockerfile`: the official `rust:1.99-slim-trixie` image plus
`pkg-config` and `libssl-dev`, which `openssl-sys` in the dependency tree needs. The two
tests run as two separate `cargo test --exact` processes (escrow/recovery first), so each
local node is fully stopped before the next starts. Debian
trixie is required because the prebuilt `near-sandbox` 2.14.0 node binary links glibc
2.39 symbols; the earlier bookworm base (glibc 2.36) fails at node start-up with
`GLIBC_2.39 not found`.

The container sees this repository and a task-specific Cargo cache (`FORECAST_NEAR_CACHE`,
default `/tmp/forecast-near-cargo`). It has no wallet/config mounts and exposes no ports.
`HOME` inside the container points into that cache so the node binary that `near-workspaces`
downloads on first use survives the `--rm` container. `sandbox/Cargo.lock` was generated by
Cargo from the `near-workspaces = 0.24.0` pin and is committed; the test command uses
`--locked`. Container limits are configurable: `FORECAST_DOCKER_MEMORY` (default `6g`),
`FORECAST_DOCKER_CPUS` (default `4`), `FORECAST_CARGO_JOBS` (default `3`), and
`FORECAST_NEAR_RPC_TIMEOUT_SECS` (default `60`, passed as `NEAR_RPC_TIMEOUT_SECS`; the
library default of 10 s was too short for a second node start in a 3.5 GiB container, and
near-sandbox 0.4 reports that timeout as "Failed to bind to available ports after 5 retries"). On the
reference machine (Intel i5, Docker Desktop VM with 3.8 GiB) the run used
`FORECAST_DOCKER_MEMORY=3500m`.

Each successful run publishes into its own unique directory under `artifacts/near-sandbox-run.*`:

- `near-receipts.json` has exactly the `forecast-near-receipts/v1` receipt fields expected by the knowledge demo.
- `near-diagnostics.json` records contract WASM hash, local network mode, assertions, transaction IDs from recovery scenarios, balance deltas and final escrowed liabilities.
- `near-dispute-cancel-diagnostics.json` records the same for the dispute/resolve/timeout/cancel test. It exports no receipts, so the knowledge demo is unaffected by it.
- `knowledge-demo/` is generated from the two exported chain receipts and the explicit synthetic-fixture consent setting.

The receipt file exports two distinct core artifact hashes: one paid `valid_wrong` delivery and one `zero_successes` delivery refunded at the acceptance deadline. Transfer-failure recovery jobs stay in diagnostics so one artifact commitment is not listed as multiple customer receipts. Failed runs remove their temporary run directory; the wrapper does not delete or overwrite prior successful runs.

Host note: this harness cannot run natively on an Intel (x86_64) Mac. `near-sandbox` 0.4.0
ships node binaries only for linux-x86_64, linux-aarch64 and darwin-arm64, and its
`near-workspaces` build script fails with `UnsupportedPlatformError` there. The Docker
route is the supported path on such hosts. To type-check the harness on the host without
the node binary: `NEAR_SANDBOX_BIN_PATH=/nonexistent cargo +1.99.1 check --tests --locked`
inside `sandbox/`.

## Chain assertions

The first test (`real_local_chain_escrow_and_transfer_recovery`) checks that the customer funds a fixed reward, assigns a worker, and the worker submits the hash from the generated core report. Customer acceptance transfers exactly the reward once. A stranger cannot accept, a second acceptance fails, and the job reaches `ACCEPTED` only after the transfer callback. The test separately submits a `zero_successes` delivery, advances sandbox block time to the acceptance boundary, and checks the customer receives the exact refund and the job reaches `REFUNDED`.

Two additional jobs exercise asynchronous failure recovery. The test deletes and recreates only ephemeral accounts on the local sandbox so the payout and refund transfer receipts fail. It checks `PAYOUT_READY` and `REFUND_READY`, then retries each fixed entitlement and verifies the exact balance increase. It also checks that outstanding reward liability reaches zero after each successful callback and at the end. These recovery cases appear in diagnostics, not the exported receipt list.

### Dispute, resolution, timeout and cancellation (second test)

`real_local_chain_dispute_resolve_timeout_and_cancel` runs five jobs on a separate node,
each with a 2 NEAR reward:

- **A. Customer dispute → resolver pays.** Resolver cannot resolve before a dispute; a
  stranger cannot dispute; the customer cannot `accept` a disputed job; a stranger and the
  customer cannot `resolve`; the named resolver pays the worker exactly the reward (status
  `ACCEPTED`); a second `resolve` and a later `timeout` are rejected.
- **B. Worker dispute → resolver refunds.** The customer receives exactly the reward;
  status `REFUNDED`.
- **C. Silent resolver.** `timeout` before the dispute deadline is rejected; after it, the
  resolver can no longer decide and a stranger's `timeout` refunds the customer exactly.
- **D. Cancel.** Contract liability equals the reward while open; a stranger cannot cancel;
  the customer's `cancel` refunds and drops liability to exactly 0; a second cancel and a
  later `assign` are rejected. The customer signs this transaction, so its balance delta is
  the reward minus its own gas: the test bounds it to `[reward − 0.05 NEAR, reward]`, attaches
  50 Tgas and waits 5 blocks for gas refunds before reading balances.
- **E. Assigned job.** `cancel` is rejected after `assign`; at the delivery deadline a
  stranger's `timeout` refunds the customer exactly.

The final liability must be 0 and the job count 5.

All deadlines come from the sandbox's current block timestamp. The harness advances blocks until the requested timestamp is reached, with a bounded loop. It does not sleep against wall-clock time.

## Limitations

- Transaction hashes are from an ephemeral local chain that no longer exists; they are
  runner evidence, not a public explorer record or a cryptographic payment proof.
- The harness uses `dev_deploy` and a separate `new` call; initialization takeover is not
  tested. Callback out-of-gas (unknown transfer outcome) is not tested on chain; see
  `docs/NEAR_CONTRACT.md`. Dispute/resolve/timeout/cancel were exercised on chain in run 2.
- The resolver is a single trusted local account; no multi-party or bonded resolution exists.
- Only the Docker runner was exercised. `rustfmt` was not run. No Testnet, Mainnet,
  wallet, real funds or external service was used.
